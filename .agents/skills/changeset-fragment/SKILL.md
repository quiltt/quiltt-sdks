# Changeset Fragments

Skill for writing Changeset fragments in the quiltt-sdks monorepo. Changesets
use the standard [Changesets CLI](https://github.com/changesets/changesets)
with a fixed versioning group — all 8 packages (`core`, `react`, `vue`,
`react-native`, `capacitor`, `android`, `flutter`, `ios`) version together.

All 8 always land on the same version, so a release can never ship them
partially. Which packages you list in the front matter does not change that —
but it does decide whose `CHANGELOG.md` records the change, which is why the
selection still matters. See [Package Selection](#package-selection).

---

## Location

Fragments live in `.changeset/*.md` at the repo root. Generated by:

```bash
pnpm changeset
```

This starts an interactive prompt to select the bump type and write the
summary. The generated file is named by Changesets (a random slug like
`twelve-kiwis-film.md`). Commit the file alongside your code changes.

**Prefer `pnpm changeset`** and fill in the summary at the interactive prompt.
It generates the front matter and the filename for you.

When the prompt is not available (an agent, a script, CI), hand-write the file
instead, matching what the CLI produces: a random-slug filename, quoted package
names, and one bump type per package.

---

## Bump Types

All 8 packages are bumped at the same time and released on one shared version,
so they always match across every platform:

| Type | When | Example |
|------|------|---------|
| `patch` | Bug fixes, minor updates, non-breaking improvements | `1.0.0 → 1.0.1` |
| `minor` | New features, backwards-compatible changes | `1.0.0 → 1.1.0` |
| `major` | Breaking changes | `1.0.0 → 2.0.0` |

### One Bump Type per Fragment

Because every package lands on the same version, a fragment declares **one**
bump type and uses it on every package it lists. Never mix them:

```yaml
# Wrong: reads as "core and react get a minor, vue gets a patch". That release
# cannot happen — vue ships the same 1.1.0 as the rest.
"@quiltt/core": minor
"@quiltt/react": minor
"@quiltt/vue": patch
```

```yaml
# Right: the most significant change in the PR sets the version for all of them.
"@quiltt/core": minor
"@quiltt/react": minor
"@quiltt/vue": minor
```

Changesets resolves a fixed group to its highest declared bump, so a lower one
does not hold a package back — it only makes that package's changelog claim a
release that never happened.

## Front Matter

`pnpm changeset` generates the YAML front matter for you — leave it as generated.
When hand-writing a fragment, copy its shape exactly: quoted package names, one
bump type each.

The front matter looks like:

```yaml
---
"@quiltt/core": patch
---
```

## Package Selection

List **every package — all 8 — in every fragment**. The fixed group versions
them together and releases them on one shared version, so a change ships to
every platform at once, and each package's `CHANGELOG.md` should say why its
version moved:

- The fixed group versions all 8 packages whatever you list.
- Only the packages you list get the summary in their `CHANGELOG.md`. A package
  that bumps without being listed records just an `Updated dependencies` entry,
  which leaves its readers unable to tell what changed.

```yaml
---
"@quiltt/core": patch
"@quiltt/react": patch
"@quiltt/react-native": patch
"@quiltt/vue": patch
"@quiltt/capacitor": patch
"@quiltt/android": patch
"@quiltt/flutter": patch
"@quiltt/ios": patch
---
```

Keep the order used in `.changeset/config.json`, so a fragment can be checked
against the group at a glance.

### Platform Wrappers Ship What They Re-export

`@quiltt/react-native` (`export * from '@quiltt/react/hooks'`) and
`@quiltt/capacitor` (`@quiltt/capacitor/react` and `@quiltt/capacitor/vue`
re-export the framework packages) run the same code as the framework packages
they wrap, and `@quiltt/android`, `@quiltt/ios`, and `@quiltt/flutter` have no
JavaScript surface at all. They are all listed anyway, because all 8 ship as one
release: a reader of any of those changelogs should be able to tell what moved
and when. Write the summary so it still reads correctly in a package that only
carries the change through a re-export — name the package whose code changed,
and describe the behaviour rather than the implementation.

## Preventing Version Drift

The fixed group is a hand-maintained list in `.changeset/config.json`. A package
under `packages/` that is missing from that list versions on its own — the one
way these packages can drift apart.

- **Adding a package?** Add it to `fixed` in the same PR, and to the package
  list at the top of this skill.
- **Verify locally:**

  ```bash
  pnpm check:version-drift
  ```

  This asserts that every package under `packages/` sits in one `fixed` group,
  that no `fixed` entry is stale, and that every released package shares a
  version.
- **CI enforces it.** `check-version-drift.yml` runs the same check whenever
  `.changeset/config.json` or a package manifest changes, so a package added
  without updating the group fails the build rather than drifting silently.

The example packages (`@quiltt/examples-*`) are excluded via `ignore` and are
expected to stay on their own version.

## Writing the Summary

The summary is the body text below the front matter. It becomes the changelog
entry in each listed package's `CHANGELOG.md`.

### Audience

Write for **developers integrating with the Quiltt SDKs**. Describe
**observable behaviour** — what the developer can now do, what works
differently, or what was broken that now works. Focus on the outcome, not
the implementation details.

### Structure

One or two paragraphs. Start with the most important thing the change does.
Include specific API names, component names, hook names, and types where
relevant.

### Style Rules

- **Imperative mood**: "Add support for…", "Fix issue where…", "Remove deprecated…"
- **Be specific**: name the package, component, hook, or type affected
- **Describe behaviour, not implementation**: "Fix `fetchWithRetry` returning `undefined` on empty responses" not "Update error handling in fetchWithRetry to check response body length"
- **No trailing period** on single-sentence summaries
- **Reference breaking changes clearly**: prefix with `**Breaking**`

### Examples

**Patch — bug fix:**

```markdown
Mark `FetchResponse<T>.data` as `T | null` to match runtime reality — `fetchWithRetry` already returns `null` when `response.json()` fails (empty or malformed bodies).

Add optional chaining guards across `react` and `vue` session, institutions, and resolvable hooks to prevent `Cannot read properties of null` crashes.
```

**Minor — new feature:**

```markdown
Add `useAccountBalance` hook to `@quiltt/react` for real-time balance updates. Returns current balance, available credit, and last-updated timestamp for the given account ID.
```

**Major — breaking change:**

```markdown
**Breaking** Remove deprecated `authenticate` prop from `QuilttProvider`. Use the `token` prop with `useQuilttSession().importSession()` instead.
```

### What to Omit

- Template comments or placeholder text
- Issue/ticket numbers in the summary body (they belong in the PR description and commit message)
- Vague entries like "Misc cleanups", "Bug fixes", "Minor improvements"
- Internal-only refactors, test additions, or CI changes that don't affect the public API or observable behaviour
- Implementation details that don't affect what the developer experiences

### One Change per Changeset

A changeset should describe one logical change. If a PR ships two unrelated
changes (e.g. a feature *and* a separate bug fix in a different area), create
two changeset files:

```bash
pnpm changeset   # first change
pnpm changeset   # second change
```

This produces two `.changeset/*.md` files. Their summaries are concatenated
into the release changelog.

## Full Workflow

1. Make code changes on a feature branch
2. Run `pnpm changeset`
3. Select all 8 packages
4. Choose the bump type (`patch` / `minor` / `major`) — it applies to all 8
5. Write the summary following the style guide above
6. Commit the generated `.changeset/*.md` file with your code changes
7. Push and open a PR
